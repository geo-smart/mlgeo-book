Part 1 of the course has five sessions, and this guide has one section for each. Every section gives a take-home message, a short list of things you should be able to do, the terms you need, and where to review. Treat the "be able to" lists as a checklist. Try each item on a dataset or repository of your own before you reopen the slides. Each row of a "Numbers to know" table names its source: a slide deck and slide title, or a book section. It also says when the number comes from the speaker notes. If the slides and the book ever define a term differently, use the book's definition. The guide ends with five ideas that run through the whole quarter and some open questions to test yourself.

## Session 1 (Wed Sep 30): Why machine learning in the geosciences

**An assistant can now write the analysis in minutes. Your job is to decide which question the data can answer, how the result will be tested, and what it means for the Earth.**

You should be able to:

- Place a published machine-learning result in one of the four uses (automation, discovery, emulation, forecasting) and explain why it does not belong in the other three.
- Report every GNSS (Global Navigation Satellite System) velocity with three things attached: its reference frame, its uncertainty, and the estimator that produced it.
- Vote on each feature of a residual time series using the three choices on lec01 "Measurement error or model error?": measurement or processing error, physics the model leaves out, or cannot tell yet. Then list the records that could settle the vote: the station log, NGL's step list, an earthquake catalog, nearby stations.
- Compare a fitted offset with its own uncertainty and with the day-to-day scatter before treating it as a signal.
- Say what each letter of FAIR asks of a dataset. Choose a license for the code and a license for the data in your repository.
- Check a paper that an assistant suggests: open the publisher's or archive's landing page and match the title, author list, year and DOI (lec01 "Pair sprint: paper, evidence, project idea", notes).

Key terms:

| Term | Meaning in this course |
|---|---|
| Automation | Doing at scale a task that people did by hand. Example: template matching on Southern California Seismic Network (SCSN) waveforms built the Quake Template Matching (QTM) catalog (lec01 "Literature example: Southern California earthquakes") |
| Discovery | Example: clustering of continuous seismic records turned up new families of repeating signals (lec01 "Four uses of machine learning in the geosciences", notes). Section 3.3 covers clustering |
| Emulation | Example: GraphCast, trained on the ERA5 reanalysis from the European Centre for Medium-Range Weather Forecasts (ECMWF), produces a 10-day global forecast in under a minute. Another example: machine-learned surrogates for ground-motion simulation (lec01 "Four uses of machine learning in the geosciences", takeaway and notes) |
| Forecasting | Examples: river floods predicted 5 days ahead in basins without gauges (Nearing et al. 2024), and El Niño predicted more than a year ahead (Ham et al. 2019) (lec01 "Machine learning results in other Earth systems", notes) |
| NGL | Nevada Geodetic Laboratory, University of Nevada, Reno: the source of the course's daily GNSS positions (1.7) |
| Trajectory model | NGL's fit to a station's position: a constant rate, annual and semi-annual terms, and steps |
| Residual | Observation minus model: what the model did not explain |
| Reference frame | The body or network that a velocity is measured against. NGL publishes each velocity in IGS20 (the International GNSS Service's realization of the International Terrestrial Reference Frame) and relative to stable North America. 1.7 explains what each frame includes |
| MIDAS | Median Interannual Difference Adjusted for Skewness: NGL's velocity estimator, built to be insensitive to steps and seasonal signals (1.7; Blewitt et al. 2016) |
| Step list | NGL's `steps.txt`: dates when a step may occur, from equipment changes and nearby earthquakes (lec01 "Measurement error or model error?", notes) |
| Correlated noise | Errors with nonzero autocorrelation at lags of days to months, so the noise power rises toward long periods. White noise has no such correlation (lec01 "What the residual contains", row E) |
| FAIR | **Findable**: a persistent identifier (DOI) and rich metadata, indexed somewhere searchable. **Accessible**: retrievable by a standard protocol such as HTTPS. "Email the author" does not count. **Interoperable**: open, documented formats and standard vocabularies. **Reusable**: a clear license and enough provenance to judge fitness for a purpose (1.1 "FAIR principles") |
| License | The terms under which others may reuse your work. Public does not mean licensed: without a license, nobody may legally reuse or modify the work (1.1 "Licenses"; lec01 "Open, reproducible science: the course standard", notes) |
| Code and data licenses | MIT or BSD for code; CC-BY or CC0 for data. A repository that holds both states the split in its README (1.1 "Licenses") |

## Session 2 (Fri Oct 2): Your reproducible workbench

**The Turing Way sorts checks of a result into four kinds, by whether the data and the analysis change. Rerunning the same code on the same data is only one of the four. Say which one you ran, and record what someone else needs to run it.**

You should be able to:

- Place any check of a result in the Turing Way two-by-two table and say what that check does not rule out (1.1 "What each test establishes").
- Take two cases through the table: the aftershock-location network (DeVries et al. 2018; Mignan and Broccardo 2019) and the Northern Hemisphere temperature reconstruction (Mann et al. 1998 through PAGES 2k 2019). Say which cells each one passed and what evidence put it there (1.1; lec02 "What each test establishes", notes).
- Score a repository on rubric v0.1 using evidence you can point to, then compare your scores with a classmate's (lec02 "Rubric calibration").
- Name the resource that limits a run (CPU, GPU, RAM, storage, network) and choose where the run should go. Follow a job through the five stages on lec02 "How an HPC job reaches hardware" (HPC: high-performance computing).
- Make a repository rerun on someone else's machine. That takes a lockfile, paths relative to the repository root (no `/Users/...`), and a README that names the command (1.9 Steps 6 and 7).
- Run Kernel > Restart Kernel and Run All Cells before you trust a notebook (1.2), and read `git diff` before every commit (1.5).

The four tests, as 1.1 prints the Turing Way table (lec02 "Same or different data, same or different analysis" shows the same table):

| | Same data | Different data |
|---|---|---|
| **Same analysis** | Reproducible: the same steps on the same data give the same answer | Replicable: the same analysis on different data gives a qualitatively similar answer |
| **Different analysis** | Robust: a different workflow on the same data gives a qualitatively similar answer | Generalisable: the answer holds across new data and new analyses |

"Robust" and "Generalisable" keep the Turing Way's wording and spelling.

Key terms:

| Term | Meaning in this course |
|---|---|
| Baseline | The simplest reasonable model a new method has to beat |
| Data leakage | Information the model would not have at prediction time reaches training or model selection, so the test score is too high (1.1; Kapoor and Narayanan 2023) |
| Observable criterion | A rubric line that names evidence anyone can inspect or rerun |
| Rubric v0.1 scale | 0 missing, 1 present but incomplete, 2 another team can verify it (lec02 "Class rubric v0.1") |
| Lockfile | `pixi.lock`, written by pixi, the package manager the course uses. It records the exact version and hash of every package for each listed platform. A clone on the same platform installs the identical set. Another operating system gets the same versions in its own builds, and results can still differ slightly (1.3 "Lockfiles are reproducibility") |
| Sandbox | Limits that a tool or service places on the software it runs, whatever packages are installed (lec02 "Software boundaries", notes) |
| Container | An environment that also carries operating-system dependencies, running on the host's hardware and kernel (lec02 "Software boundaries", notes) |
| Login node | The shared machine you connect to first on a cluster such as Hyak, UW's HPC system |
| Compute node | A machine the scheduler assigns to a job |
| Scheduler | The program that queues resource requests (cores, memory, GPUs, wall time) and starts a job when a matching allocation is free (lec02 "How an HPC job reaches hardware") |
| GPU utilization | A GPU speeds up parallel arithmetic only. It waits whenever the CPU-side data loader or the file system cannot feed it data fast enough (lec02 "CPU and GPU execution models", notes) |
| Provenance | Source revision and uncommitted changes; data identifiers, versions, the time window and other preprocessing parameters; environment specification and lockfile; command, configuration, random seed and requested resources; logs, warnings and output checksums (lec02 "Minimum computational provenance") |
| Smoke test | A short run that checks three things: the packages import, a small calculation with a known answer returns it, and the run reaches the end. In your repository it is `smoke_test.py`, run with `pixi run smoke`, which checks that a line rising 2.5 mm/yr gives slope 2.5 (1.9 Steps 5 and 6) |
| Staging area | Git's list of the changes to include in the next commit. `git status` shows it (1.5) |
| Hidden state | Anything the running kernel remembers that the visible cells, run top to bottom, would not produce (1.2) |

## Session 4 (Wed Oct 7): Data streams, formats, and the first real dataset

**How a dataset is stored and which copy you read are scientific choices. Match the container to the kind of data, and record exactly which version you used.**

You should be able to:

- Assign a dataset to one of the three streams (regular series, gridded fields, irregular sparse points) and choose an array or a data frame to hold it.
- Explain what a CSV file throws away, and choose among CSV, Parquet, netCDF and Zarr for a given size and use.
- Decide whether to pin a file's checksum (a released file) or log it on every run (a file that keeps changing), and say what a hash mismatch means.

## Session 5 (Fri Oct 9): Cleaning tabular data

**Every cleaning rule changes a number that a conclusion rests on. Base each rule on the column's physics and metadata, and log what it changed.**

You should be able to:

- Find the sentinel values in a table and write each replacement rule, with the count it changed and the reason, into the cleaning log.
- Recognize values held at a reporting floor, predict which way they bias a mean or a trend, and explain why deleting them does not remove the bias.
- Ask what caused each gap, and say when dropping incomplete rows deletes the very events the study is about.
- Check column types after every cleaning step, and show how a completeness cut changes a catalog statistic.

Key terms:

| Term | Meaning in this course |
|---|---|
| Sentinel | A placeholder value (0, -999) that an instrument writes when it has no measurement |
| Censored value | A value reported as the floor (or ceiling) because the true value lies beyond it. `isna()` does not flag it (lec05 "Values censored at a reporting floor", notes; 2.4) |
| MCAR | Missing completely at random: the gap has nothing to do with the value |
| MNAR | Missing not at random: the value itself causes the gap, as when the flood drowns the gauge |
| Dtype drift | A cleaning step silently changes a column's type, after which numeric tools skip the column |
| Magnitude of completeness (Mc) | The magnitude above which a catalog records essentially every event |
| b-value | The slope of the magnitude-frequency relation, N(≥M) ∝ 10^(-bM) |
| Cleaning log | Each rule, the count of values it changed, and the reason, recorded in `cleaning_log.csv` and the data card |

## Five ideas that carry the quarter

1. **Name the test.** Say whether the data changed, the analysis changed, both or neither. Report the cell of the Turing Way table that your evidence supports.
2. **Beat a baseline, on data the model never saw.** A complex model earns its place only by doing better than the simplest reasonable one, on a test set that shares nothing with training.
3. **Know the answer before you trust the method.** lec05 could measure the bias from a reporting floor exactly because the generator returned the uncensored truth. Your smoke test's 2.5 mm/yr slope applies the same idea to code.
4. **The specification decides the number.** Component, interval, frame, data version and cleaning rules all change the answer. Write them down before you ask a person or an agent.
5. **Check against a record the model did not write, and leave one of your own.** That means checkable rules, disclosed AI help, and the commit that ran.

## Check yourself

None of these has a single right answer. Write a paragraph for each, then compare with a classmate.

1. P395's east residual starts to decline months before its 2016 equipment changes (lec01 "What the residual contains", row D). What data, from this station or others, would tell you whether part of that decline is ground motion?
2. P563 subsides 7.2 mm/yr (lec04). Propose two observations that would separate groundwater extraction from a tectonic cause, and say which data stream each belongs to.
3. Pick one result from your own field. For each of the four cells of the Turing Way table, describe a concrete test that would place the result in that cell, and what the test would cost.
4. Estimate the size of the dataset you plan to use for your project. Which resource will limit your first full run, and where will you run it? What would you write in the README so someone else can request the same resources?
5. GPT-4 gave a confidence label to all 300 IPCC statements (lec03). Why is a confident answer to every item not evidence of skill? How would you set up an independent check for a question in your project?
6. Choose one cleaning rule you expect to apply to your project data. Write it as an AGENTS.md rule, then describe what in a transcript or a commit would show that the agent followed it.
7. Keeping only events at or above Mc moved the b-value from 0.43 to 0.81 (lec05). Name a quantity in your own data that depends on a similar cut, and say how you would report the choice.
