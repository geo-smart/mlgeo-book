Your repository is public, so read each log before you commit it: remove tokens, passwords and personal details. A quick check is `grep -n -i "token\|password\|ghp_" AI_logs/*.md`. If you used no AI tool outside Step 8, say so in `AI_logs/README.md`; an honest "none" earns the points.

## Step 1 — Install pixi

On macOS with [Homebrew](https://brew.sh), `brew install pixi` works too. After installing, close and reopen the terminal so your shell picks up the new PATH.

Success looks like: a version number prints, e.g. `pixi 0.48.0`. If the command is not found, restart the terminal; if it is still not found, the installer prints the line to add to your shell profile — add it and restart again.

**Verify:**

Success looks like: git prints a version 2.40 or newer, and `gh auth status` reports `Logged in to github.com` with your user name.

## Step 5 — Smoke test: run a notebook

A **smoke test** is a short, fast check that the basic machinery runs from start to finish: the packages import, a small calculation with a known answer returns that answer, and output appears. The name comes from hardware testing: switch the new device on and check that nothing starts smoking. A smoke test cannot show that a scientific result is right. It shows that the setup does not fail at once, in seconds instead of an hour into a real run. Run it first on any new machine and after every environment change. It is also the first thing another person runs to find out whether your repository works on their computer. This step smoke-tests the course book's environment. Step 6 adds a smoke test to your own repository.

In JupyterLab, open any Chapter 1 notebook — for example `book/Chapter1-GettingStarted/1.7_get_geodetic_gnss.ipynb` — and run the first few cells (`Shift-Enter`).

Success looks like: the import cells complete without `ModuleNotFoundError`, and the first data or plot cell produces output. If imports fail, you are probably running a kernel outside the pixi environment: check that you launched JupyterLab with `pixi run jupyter lab` from the `mlgeo-book` directory.

## Step 6 — Push a change to your own repository

Close the loop by pushing a commit to `MLGEO2026_UWNETID`. In a terminal, go to your repository from step 3, edit `README.md` (add a title line, your name, and one sentence on what you want out of this course), then:

    git add README.md
    git commit -m "Introduce myself in the README"
    git push

While you are at it, add the course environment to your repository, so your own work is reproducible from day one. The book keeps a manifest written for student repositories in its `environments/student/` folder. Copy it and its lockfile to the top of your repository, then install:

    cp ../mlgeo-book/environments/student/pixi.toml ../mlgeo-book/environments/student/pixi.lock .
    pixi install

(Adjust the `../mlgeo-book/` path if your folders live elsewhere.) Do not copy the book's top-level `pixi.toml` instead. It installs the book's own `mlgeo_synth` package from the book's folder, which does not exist in your repository, so every `pixi run` there fails with "does not appear to be a Python project"; its build tasks also expect the book's folders. The student manifest pins the same package versions as the book's lockfile, installs `mlgeo_synth` from a snapshot of the book on GitHub, leaves out the tools that build the book, and adds `pixi run lab` to start JupyterLab in your repository. Because pixi reuses the packages it downloaded in step 4, this install takes a minute or two rather than several.

Now give your repository its own smoke test. Save this as `smoke_test.py` in the repository:

```python
"""Smoke test: check that the course environment runs before doing real work."""
import platform

import numpy as np
import pandas as pd
import xarray as xr

# A calculation with a known answer: a line rising 2.5 mm/yr must give slope 2.5.
t = np.arange(0.0, 10.0, 0.1)
slope = np.polyfit(t, 2.5 * t + 1.0, 1)[0]
assert abs(slope - 2.5) < 1e-9, f"expected slope 2.5, got {slope}"

print(f"Python {platform.python_version()} on {platform.system()} {platform.machine()}")
print(f"numpy {np.__version__}, pandas {pd.__version__}, xarray {xr.__version__}")
print("smoke test passed")
```

Register it as a pixi task and run it:

    pixi task add smoke "python smoke_test.py"
    pixi run smoke

Success looks like: the last line printed is `smoke test passed`. Add a **How to run** section to `README.md` that names the command (`pixi run smoke`) and records the operating system and machine type from the first printed line, for example `Tested on Darwin arm64`. Then commit and push:

    git add pixi.toml pixi.lock smoke_test.py README.md
    git commit -m "Add course environment and smoke test"
    git push

**Verify:** reload the repository page on GitHub.

Success looks like: your README edit, the two pixi files, and `smoke_test.py` are visible on GitHub, and the commits appear under **Commits** with your user name attached. In class on Wednesday Oct 7, a classmate will clone your repository and run `pixi run smoke` with only your README as a guide.

## Step 7 — Write an AGENTS.md

An instruction file tells your coding agent how work is done in your repository. AGENTS.md is plain Markdown with no required fields ([agents.md](https://agents.md/)); what makes one useful is its structure and whether its rules can be checked. Session 3 derived one from the class rubric; now give `MLGEO2026_UWNETID` its own, organized around one goal: **any result in this repository can be regenerated from a fresh clone with commands written down in the repository**. An agent that follows the file should leave your repository more reproducible than it found it, never less.

Create `AGENTS.md` at the top of the repository with these six headings, in this order. The first is a short paragraph; each of the other five holds rules and maps onto a dimension of rubric v0.1 (Session 2):

| Heading | Rubric v0.1 dimension it serves | What its rules control |
|---|---|---|
| Project | Scientific claim | what the repository is for and what "reproducible" means here |
| Environment and compute | Environment and compute | how packages are installed and code is run |
| Data and provenance | Data and provenance | where data and published values come from, and how that is recorded |
| Code and workflow | Code and workflow | paths, notebooks, and the commands that regenerate outputs |
| Reporting and credit | Publication and credit | how numbers are stated and how AI help is credited |
| Verification | Evaluation | what the agent must run and show before it reports a result |

Write at least five rules in total, with at least one under each of the five rule headings. Start from this template and adapt it:

```markdown
# AGENTS.md for MLGEO2026_UWNETID

## Project
Course repository for ESS 469/569, Autumn 2026: homeworks and the final project.
Every number and figure here must be regenerated from a fresh clone using
the commands in README.md.

## Environment and compute
- Run all code through `pixi run`; add packages only with `pixi add`, and
  commit pixi.toml and pixi.lock together.
- Do not install packages with pip or conda outside pixi.

## Data and provenance
- Fetch values that a provider publishes (station coordinates, velocities,
  catalogs) and cite the URL and retrieval date; do not recompute or retype them.
- Download data with a script in this repository, not by hand, and record the
  dataset DOI or URL, version, and retrieval date in README.md.
- Never modify raw data files; write processed data to a separate folder.

## Code and workflow
- Use paths relative to the repository root; no absolute paths such as /Users/...
- Every notebook must run top to bottom after Restart Kernel and Run All Cells.
- Every reported number and figure comes from a command listed in README.md.

## Reporting and credit
- State the reference frame, units, and time window of every number.
- Mark AI-drafted commits: "AI-assisted: <tool>, <what it drafted>".

## Verification
- Run `pixi run smoke` before reporting any result, and show its last line.
- Report the exact commands you ran and the commit hash they ran on.
- If a check fails or a value cannot be fetched, say so; do not substitute an estimate.
```

Test each rule with two questions before you keep it. Can someone settle it yes or no by reading the agent's transcript or your commits? Does it protect a rerun from a fresh clone? "Write clean code" fails the first question and does not count; "use descriptive variable names" passes the first and fails the second, so it belongs in a style section, not in these five.

Claude Code reads `AGENTS.md` when the repository has no `CLAUDE.md`; if you keep a `CLAUDE.md` as well, add the line `@AGENTS.md` to it so that both load. [agents.md](https://agents.md/) lists the other agents that read the file and how to configure them.

    git add AGENTS.md
    git commit -m "Add agent instructions from the class rubric"
    git push

Success looks like: `AGENTS.md` is visible on GitHub with the six headings and at least five checkable rules, at least one under each rule heading. Later in the quarter, [6.3](../Chapter6-AgenticAI/6.3_build_an_eval_set.ipynb) turns a specification like this one into an evaluation set and measures whether an agent follows it.

## Step 8 — Verify your repository three ways

A score of 2 on the class rubric means *another team can verify it*. In this step you collect three kinds of verification of the same commit and compare them: a person who reruns your repository, a coding agent that reruns it, and chatbots that only read it. They will not agree, and the disagreements are the point. Budget about 45 minutes.

Write down the commit that all three will check:

    git rev-parse --short HEAD

Every verifier scores the same four rubric dimensions on the 0/1/2 scale (0 missing, 1 present but incomplete, 2 another team can verify it): **Environment and compute, Code and workflow, Data and provenance, Publication and credit**. Your repository has no dataset yet, so "Data and provenance" may honestly be N/A; a verifier that gives it a 2 is telling you something about the verifier.

**8a. Human verification (runs the code).** In class on Wednesday Oct 7, a classmate cloned your repository and ran `pixi run smoke` from your README. Record who it was, the date, the commit, what they ran, whether it passed, and where the README left them guessing. If you missed that session, ask a classmate now. Rerunning it yourself in an empty folder is the fallback, and you should say that you did, because the author is the weakest possible verifier.

**8b. Agent verification (runs the code).** Clone your repository into a fresh folder, so the agent cannot use anything on your machine that a stranger would not have, and start your coding agent there:

    cd /tmp
    git clone https://github.com/YOURUSERNAME/MLGEO2026_UWNETID verify_hw1
    cd verify_hw1

Give it this prompt:

> You are verifying that this repository is reproducible. Use only README.md and AGENTS.md as instructions. Install the environment, run the documented commands, and list every command you ran with the last line of its output. Then score the repository 0, 1, 2 or N/A on Environment and compute, Code and workflow, Data and provenance, and Publication and credit (0 missing, 1 present but incomplete, 2 another team can verify it), quoting the file and line that supports each score. Do not edit any file.

Then check the agent, not just its answer: do the commands it lists appear in its actual tool calls, and does `git status` in `verify_hw1` show no changes? Save the session to `AI_logs/` in your own repository, not in `verify_hw1`.

**8c. Chatbot verification with UW Purple (reads, does not run).** [Purple](https://it.uw.edu/guides/artificial-intelligence/purple/) is UW's own AI platform: sign in at [purple.uw.edu](https://purple.uw.edu/) with your UW NetID. UW-IT states that what you enter is not used to train public models, and that Purple gives access to several models in one place. Run the prompt below with **at least two different models** and save each conversation as its own file in `AI_logs/`:

> Here is the public GitHub repository https://github.com/YOURUSERNAME/MLGEO2026_UWNETID at commit <your hash>. First, quote the first line of README.md and the first line of smoke_test.py exactly. If you cannot open the repository, say so and stop. Then score it 0, 1, 2 or N/A on Environment and compute, Code and workflow, Data and provenance, and Publication and credit (0 missing, 1 present but incomplete, 2 another team can verify it), quoting the file and line that supports each score.

The first request is a reading check. Compare the quoted lines with your files: a model that quotes lines your repository does not contain has scored a repository it never saw. Record that as a finding about the model, not as a failure of yours. If a model says it cannot open the link, upload `README.md`, `AGENTS.md`, `pixi.toml` and `smoke_test.py` as files and ask again. Share only what is already public in your repository; never paste tokens or passwords.

**8d. Compare and report.** Create `VERIFICATION.md` at the top of the repository with the commit hash and this table:

| Verifier | Tool and model | Ran the code? | Read the repo correctly? | Environment and compute | Code and workflow | Data and provenance | Publication and credit |
|---|---|---|---|---|---|---|---|
| Human: name | none | yes | yes | | | | |
| Agent | e.g. Claude Code, model name | yes | | | | | |
| Chatbot | Purple, model 1 | no | | | | | |
| Chatbot | Purple, model 2 | no | | | | | |

Below the table, write three to five sentences: where the verifiers disagree; which one you trust for Environment and compute, and why; and one change you made to `README.md` or `AGENTS.md` because of what they found. Commit that change and `VERIFICATION.md`:

    git add VERIFICATION.md README.md AGENTS.md AI_logs/
    git commit -m "Record human, agent and chatbot verification of HW1"
    git push

Success looks like: `VERIFICATION.md` is visible on GitHub with the commit hash, four rows (one human, one agent, two Purple models), and your comparison. The same comparison returns in [6.2](../Chapter6-AgenticAI/6.2_critical_evaluation.ipynb) on Oct 23, where model graders get bias controls, and in [6.3](../Chapter6-AgenticAI/6.3_build_an_eval_set.ipynb) on Nov 13, where one run becomes many.
