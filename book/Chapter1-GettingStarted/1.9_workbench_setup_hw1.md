## Step 1 — Install pixi

**macOS / Linux / WSL2**, in a terminal:

    curl -fsSL https://pixi.sh/install.sh | sh

On macOS with [Homebrew](https://brew.sh), `brew install pixi` works too. After installing, close and reopen the terminal so your shell picks up the new PATH.

**Verify:**

    pixi --version

Success looks like: a version number prints, e.g. `pixi 0.48.0`. If the command is not found, restart the terminal; if it is still not found, the installer prints the line to add to your shell profile — add it and restart again.

## Step 2 — Install git and create a GitHub account

Check whether git is already installed:

    git --version

If not: on macOS, running that command triggers the Xcode Command Line Tools installer (accept it); on Ubuntu/WSL2, `sudo apt install git`.

Then:

1. Create an account at [github.com](https://github.com/) and set up two-factor authentication (see [1.5](1.5_version_control_git.md#authentication)).
2. Tell git who you are, using the same user name and email as the GitHub account:

       git config --global user.name "superseismo"
       git config --global user.email "superseismo@uw.edu"

3. Install the [GitHub CLI](https://cli.github.com/) and authenticate:

       gh auth login

   Accept the defaults (GitHub.com, HTTPS, login with a web browser) and follow the browser prompts.

**Verify:**

    git --version
    gh auth status

Success looks like: git prints a version 2.40 or newer, and `gh auth status` reports `Logged in to github.com` with your user name.

## Step 3 — Create your course repository

Create your personal course repository, named `MLGEO2026_UWNETID` (your NetID in capitals, e.g. `MLGEO2026_SUPERSEISMO`). This repository holds your homeworks and project work for the quarter. Create it **once**, with one command:

    gh repo create MLGEO2026_UWNETID --public --add-readme --license mit --clone

This creates the repository on GitHub with a README and an MIT license, and clones it into a folder of the same name. Run it from the directory where you keep course work — outside cloud-synced folders such as Dropbox or Google Drive.

(No terminal? The browser equivalent is in [1.5](1.5_version_control_git.md#create-a-new-repository); then clone it.)

**Verify:** open `https://github.com/YOURUSERNAME/MLGEO2026_UWNETID` in a browser.

Success looks like: the repository page loads and shows a README and a LICENSE file, and `ls MLGEO2026_UWNETID` on your computer shows the same files.

## Step 4 — Clone the course book and install its environment

Clone the course repository and let pixi build the environment from the lockfile:

    git clone https://github.com/geo-smart/mlgeo-book.git
    cd mlgeo-book
    pixi install

The first `pixi install` downloads a few gigabytes of packages; expect several minutes on a fast connection. Then launch JupyterLab from inside the environment:

    pixi run jupyter lab

**Verify:** JupyterLab opens in your browser (or prints a `http://localhost:8888/lab?token=...` URL to open).

Success looks like: the JupyterLab interface loads and its file browser shows the `book/` folder. Stop it later with `Ctrl-C` in the terminal.

```{tip}
`pixi run` always uses the project's own environment — there is no environment to activate or forget. If `pixi install` fails partway (network hiccup), run it again; it resumes.
```

## Step 5 — Smoke test: run a notebook

A **smoke test** is a short, fast check that the basic machinery runs from start to finish: the packages import, a small calculation with a known answer returns that answer, and output appears. The name comes from hardware testing: switch the new device on and check that nothing starts smoking. A smoke test cannot show that a scientific result is right. It shows that the setup does not fail at once, in seconds instead of an hour into a real run. Run it first on any new machine and after every environment change. It is also the first thing another person runs to find out whether your repository works on their computer. This step smoke-tests the course book's environment. Step 6 adds a smoke test to your own repository.

In JupyterLab, open any Chapter 1 notebook — for example `book/Chapter1-GettingStarted/1.7_get_geodetic_gnss.ipynb` — and run the first few cells (`Shift-Enter`).

Success looks like: the import cells complete without `ModuleNotFoundError`, and the first data or plot cell produces output. If imports fail, you are probably running a kernel outside the pixi environment: check that you launched JupyterLab with `pixi run jupyter lab` from the `mlgeo-book` directory.

## Step 6 — Push a change to your own repository

Close the loop by pushing a commit to `MLGEO2026_UWNETID`. In a terminal, go to your repository from step 3, edit `README.md` (add a title line, your name, and one sentence on what you want out of this course), then:

    git add README.md
    git commit -m "Introduce myself in the README"
    git push

While you are at it, copy the environment files from the course book into your repository, so your own work is reproducible from day one:

    cp ../mlgeo-book/pixi.toml ../mlgeo-book/pixi.lock .
    pixi remove --pypi mlgeo-synth

(Adjust the `../mlgeo-book/` path if your folders live elsewhere.) The second command removes one line that only makes sense inside the book: it installs the book's own `mlgeo_synth` package from the book's folder, which does not exist in your repository. Without the removal, every `pixi run` in your repository fails with "does not appear to be a Python project". Every other package keeps the exact version pinned in the book's lockfile.

Now give your repository its own smoke test. Save this as `smoke_test.py` in the repository:

```python
"""Smoke test: check that the course environment runs before doing real work."""
import platform

import numpy as np
import pandas as pd
import xarray as xr

# A calculation with a known answer: a line rising 2.5 mm/yr must give slope 2.5.
t = np.arange(0.0, 10.0, 0.1)
slope = np.polyfit(t, 2.5 * t + 1.0, 1)[0]
assert abs(slope - 2.5) < 1e-9, f"expected slope 2.5, got {slope}"

print(f"Python {platform.python_version()} on {platform.system()} {platform.machine()}")
print(f"numpy {np.__version__}, pandas {pd.__version__}, xarray {xr.__version__}")
print("smoke test passed")
```

Register it as a pixi task and run it:

    pixi task add smoke "python smoke_test.py"
    pixi run smoke

Success looks like: the last line printed is `smoke test passed`. Add a **How to run** section to `README.md` that names the command (`pixi run smoke`) and records the operating system and machine type from the first printed line, for example `Tested on Darwin arm64`. Then commit and push:

    git add pixi.toml pixi.lock smoke_test.py README.md
    git commit -m "Add course environment and smoke test"
    git push

**Verify:** reload the repository page on GitHub.

Success looks like: your README edit, the two pixi files, and `smoke_test.py` are visible on GitHub, and the commits appear under **Commits** with your user name attached. In class on Wednesday Oct 7, a classmate will clone your repository and run `pixi run smoke` with only your README as a guide.

## Step 7 — Write an AGENTS.md

An instruction file tells your coding agent how work is done in your repository. Session 3 derived one from the class rubric; now give `MLGEO2026_UWNETID` its own. Create `AGENTS.md` at the top of the repository with at least five rules, each a check that someone can settle by reading the agent's output or your commits. Start from this template and adapt it:

```markdown
# AGENTS.md for MLGEO2026_UWNETID
## Environment
- Run all code through `pixi run`; add packages only through pixi.toml.
- Run `pixi run smoke` before reporting any result.
## Data
- Fetch values that a provider publishes (station coordinates, velocities,
  catalogs) and cite the URL and retrieval date; do not recompute or retype them.
- Cite every dataset by DOI in the README.
## Reporting
- State the reference frame, units, and time window of every number.
- Mark AI-drafted commits: "AI-assisted: <tool>, <what it drafted>".
```

A rule such as "write clean code" cannot be checked and does not count toward the five. Claude Code reads `AGENTS.md` when the repository has no `CLAUDE.md`; if you keep a `CLAUDE.md` as well, add the line `@AGENTS.md` to it so that both load. [agents.md](https://agents.md/) lists the other agents that read the file and how to configure them.

    git add AGENTS.md
    git commit -m "Add agent instructions from the class rubric"
    git push

Success looks like: `AGENTS.md` is visible on GitHub with at least five checkable rules. Later in the quarter, [6.3](../Chapter6-AgenticAI/6.3_build_an_eval_set.ipynb) turns a specification like this one into an evaluation set and measures whether an agent follows it.
